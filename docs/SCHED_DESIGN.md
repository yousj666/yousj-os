# Yousj OS · 进程与调度设计

> 状态：设计稿，待总协调评审。阶段 1 第 3 步（PMM、VMM 之后）。
> 前置依赖：VMM_DESIGN.md（地址空间 `vmm_space`、CR3 切换约定）、
> `syscall.h` 已保留的号码。本文所有新增结构、函数与常量均为
> **接口提案**，标注为「提案」；未获总协调批准前，不视为
> `kernel/include/yousj/` 的既定接口，不得据此自行改头文件。
> 现状事实：内核尚无 IDT、无定时器、无中断处理，`kmain.c` 在 PMM
> 自检后直接 `cli; hlt` 停机；调度器要用的每一块地基都要在本设计
> 中显式声明依赖，不假装已存在。

## 1. 目标与非目标

### 1.1 本阶段目标

1. 内核里能同时存在多个执行流，按时间片轮转，谁也不许独占 CPU
   （先协作式打通、再抢占式收尾，见 §4）。
2. 有一份明确的任务结构与状态机，使 exit/wait/kill 这类进程语义
   有地方落，为阶段 2 的 fork/exec 与 Shell/init 铺路。
3. 给出从「内核线程」走到「第一个用户进程 init」再到「Shell 能敲
   命令」这一里程碑（服务器版第一里程碑的后半段）的完整路径，
   每一步都可在串口上验证。
4. 调度核心逻辑（队列、状态迁移、挑选下一个）可宿主机单测，
   沿用 PMM/VMM 的 hosted 测试传统；只有上下文切换汇编与中断
   入口必须开机验证。

### 1.2 非目标

- 不做多核（SMP）调度：单核、单个全局运行队列、无 per-CPU 结构。
  任务结构里不预埋锁字段充样子，将来上 SMP 时正经加。
- 不做优先级/实时/CFS 类公平调度：本阶段只有轮转（见 §4 的理由）。
  Linux 兼容程序对调度策略不敏感（它们只依赖时间片存在、进程语义
  正确），策略可以后换，语义不能后补。
- 不做完整信号机制：只预留 kill 的最小语义（§6.4），信号递送、
  信号掩码、sigaction 等留阶段 2 随 ELF/Shell 一起补。
- 不做线程组、命名空间、cgroup、凭据（uid/gid 先以字段占位，恒为
  0/root 语义在注释中写明，不假装做了权限模型）。

## 2. 总体选型：先内核线程，后用户进程

### 2.1 两个候选

- **直接上用户进程**：调度器一出生就切换 CR3、跨特权级、走 ELF
  加载。问题是它同时依赖 VMM 的用户空间、ELF 加载器、syscall 入口
  三件尚未存在的东西，任何一处 bug 都表现为「Ring 3 里 #PF 且没有
  任何输出」，在只有串口的无头环境里调试成本极高，且分不清是
  调度错了还是加载错了。
- **先内核线程**：所有任务都是 Ring 0 的内核函数，共用内核地址
  结构，调度器只管「保存/恢复寄存器 + 换栈」。上下文切换这一最
  脆弱的部件可以单独验证（两个线程轮流打印），与 VMM 的用户空间
  解耦；之后用户进程被实现为「带自有 `vmm_space`、且首次运行要
  落到 Ring 3 的任务」，复用同一套切换机制。

### 2.2 推荐：内核线程优先（结论）

**先做内核线程并把上下文切换验透，再在同一任务结构上长出用户
进程。** 内核线程不是绕路：idle 线程、将来的内核工作线程（如
控制台输入处理、后续文件系统回写）本来就是内核线程，写了不废。
用户进程路径只多三件事——自有地址空间、Ring 3 落点、syscall
进出——每件都单独设里程碑（§8），出问题时能定位到具体一件。

## 3. 任务结构提案

### 3.1 概念划界（先钉死词义）

本阶段 **一个 task = 一个执行流 = 一个调度单位**。用户进程在
本阶段是单线程的，于是 pid 与 tid 数值相同；将来 clone(CLONE_VM)
做多线程时，再引入「线程组共享一个 `vmm_space` 与文件表、pid 取
组长 tid」的扩展，任务结构中以 `mm` 指针共享的方式天然支持，
不在本阶段预写线程组字段。内核线程是 `mm == NULL` 的 task。

### 3.2 `struct task`（提案）

```c
/* 提案，待批准。字段按用途分组，注释标明哪一组何时才真正用上。 */
enum task_state {               /* 提案 */
    TASK_READY,                 /* 在运行队列中，等待被挑 */
    TASK_RUNNING,               /* 正在 CPU 上（全局至多一个） */
    TASK_BLOCKED,               /* 在某个等待队列/睡眠中，不在运行队列 */
    TASK_ZOMBIE,                /* 已 exit，等待父进程 wait4 回收 */
    TASK_DEAD,                  /* 已被回收，结构即将释放（过渡态） */
};

struct task_context {           /* 提案：只含被调用者保存的寄存器，见 §5 */
    uint64_t rsp;               /* 恢复点栈指针；其余寄存器压在此栈上 */
};

struct task {                   /* 提案 */
    /* 身份与状态 */
    uint64_t        tid;        /* 同时是单线程进程的 pid */
    uint64_t        parent_tid; /* 0 表示无父（idle 与 init） */
    enum task_state state;
    char            name[16];   /* 仅供串口日志，如 "idle" "init" */

    /* 调度 */
    struct task_context ctx;    /* 切换时保存的 rsp，见 §5 */
    uint64_t        timeslice_left; /* 剩余 tick 数，见 §4 */
    uint64_t        total_ticks;    /* 累计运行 tick，统计/自检用 */
    struct task    *rq_next;    /* 运行队列单链表指针 */
    struct task    *all_next;   /* 全部任务链表（kill/wait 查表用） */

    /* 地址空间与栈 */
    struct vmm_space *mm;       /* NULL = 内核线程，借用内核主空间 */
    uint64_t        kernel_stack_top; /* 本任务进入内核时用的栈顶：
                                   内核线程即其唯一栈；用户任务为
                                   syscall/中断时的内核栈 */
    /* 内核栈大小提案：16 KiB（4 页，pmm_alloc_pages(4) 连续申请，
       下方留 1 页 guard 不映射）。理由见 §3.3。 */

    /* 进程语义（阶段 1 只填最小子集） */
    int             exit_status;    /* exit 时写入，wait4 读 */
    struct task    *wait_queue_head;/* 在此任务上等 wait4 的父/子关系
                                       以全表扫描代替专用队列亦可，
                                       见 §6.3 的简化约定 */

    /* 用户态落点（仅用户任务；内核线程为 0） */
    uint64_t        user_ip;    /* 首次进 Ring 3 的入口（ELF e_entry） */
    uint64_t        user_sp;    /* 首次进 Ring 3 的栈顶 */

    /* 文件与当前目录：属 VFS 地盘，本结构只预留指针位置，
       阶段 2 由 VFS 设计定其结构，本提案不展开 */
    void           *files;      /* 提案占位，NULL 直到 VFS 落地 */
};
```

全局量（提案）：`current`（当前任务指针）、任务全表头、运行队列
头尾、`next_tid` 计数器（从 1 起，1 号留给 init；idle 为 0 号且
永不进入全表语义上的「进程」序列，`getpid` 对 idle 不可达）。

### 3.3 内核栈的取舍

- 每个任务一张独立内核栈，不共用。共用栈（如极早期单栈）在嵌套
  中断与阻塞切换下必炸，没有讨论余地。
- 大小提案 16 KiB：当前内核调用链浅（串口打印、页表走表），4 KiB
  名义够用，但串口格式化、将来 syscall 参数拷贝与驱动调用链深度
  不可控，16 KiB 是「多花 3 页、少一类栈溢出玄学 bug」的划算交易；
  栈底再留一页 guard（分配 5 页、最下一页不映射），溢出即 #PF
  而不是悄悄踩坏相邻页表页。
- 栈内存来自 PMM 的连续分配 `pmm_alloc_pages`：连续在这里不是
  页表那种硬需求，只是一次分配、一个基址好记账；若碎片化导致
  连续 5 页失败，任务创建返回 `-ENOMEM` 即可（服务器进程数
  远未到会把 8 GiB 碎片化到连 5 页都凑不出的量级），不在本阶段
  为此做分段栈。

## 4. 调度算法与时间片来源

### 4.1 算法：单队列 FIFO 轮转（Round-Robin）

- 一个全局运行队列（单链表，队尾入队）。`schedule()` 从队头取
  下一个 READY 任务，当前任务若仍可运行则排到队尾。
- 挑选是 O(队列长)，阶段 1 任务数个位数到两位数，不优化；
  结构上以后换多级反馈队列只动挑选函数，状态机与切换不动。
- idle 任务（0 号）不在运行队列中：仅当队列为空时由 `schedule()`
  兜底选中，其栈与上下文独立；它只做 `hlt` 等中断，任何 tick
  到来再重新挑队列，避免忙等烧 CPU 掩盖「其实没活干」的事实。
- 阻塞与唤醒：任务阻塞时自设 state=BLOCKED 并调用 `schedule()`
  让出；唤醒方（如控制台输入、wait 的子进程退出）把目标任务置
  READY 并入队队尾。本阶段等待队列先用「按条件挂在单个等待头
  指针上」的最简实现，条件多了再拆，不预建通用 waitqueue 框架。

### 4.2 时间片与定时器：**当前不存在，这是硬依赖**

现状必须写清：内核**没有 IDT、没有 PIC/APIC 初始化、没有
PIT/LAPIC 定时器驱动、从未执行 `sti`**（kmain 的 halt 还是
`cli; hlt`）。所以「时间片」现在没有来源，调度器分两步落地：

**第一步：协作式。** 无定时器，任务靠主动调用提案的 `sched_yield()`
（及阻塞点顺带让出）切换。目的纯粹是先验上下文切换、队列与状态机，
不承诺公平性。此步不依赖任何新硬件代码，可紧接 VMM 之后做。

**第二步：抢占式。** 补齐下列依赖后才有真时间片，缺一不可：

1. IDT + 异常/IRQ 最简处理框架（其中 #PF 转储一份即可，顺带补上
   VMM_DESIGN.md §9 提出的前置需求，两份设计在此汇合）；
2. 中断控制器：先 8259 PIC（bring-up 最短路径）或直接 LAPIC
   （经 boot.h 的 RSDP 走 ACPI 探测）——**提案先 PIC**，LAPIC 留作
   上 SMP 前的替换项，避免在调度阶段同时啃 ACPI；
3. 定时器源：PIT 通道 0，频率提案 `HZ = 100`（每 tick 10 ms），
   服务器无头场景不需要 1000 Hz 的细粒度，低频少打扰、串口日志
   里的时间也好读；
4. tick 处理：IRQ0 → `current->timeslice_left--`，归零则置
   「需要重调度」标志，在中断返回前（仍在内核态、当前任务内核栈上）
   调用 `schedule()`；同时给 `total_ticks` 记账，并唤醒到期的
   睡眠者（nanosleep 的实现基础，见 §6.5）。

时间片长度提案：默认 **5 个 tick（50 ms）**，任务创建时写入
`timeslice_left`，用尽且被换下时重置为满额。50 ms 对串口 Shell
交互足够跟手，对批处理也不至于切换频繁到掩盖真实负载；数值做成
单个常量（提案 `YOUSJ_SCHED_SLICE_TICKS`），改频率只改一处。

抢占的边界：只在「中断返回到用户态之前」与「中断返回到可抢占
内核态」两个点检查重调度标志；内核临界区（操作运行队列、页表
时）通过关中断（`cli`）保护，本阶段单核下关中断即等于加锁，
所有队列/全表操作函数的注释里须写明「调用时中断须已关或由
调用方关」这一约定，不留口头默契。

## 5. 上下文切换：保存什么与汇编要点

### 5.1 保存集合：只存被调用者保存寄存器 + rsp

切换发生在函数调用层面（`schedule()` 调用切换函数），遵循
System V AMD64 调用约定即可只保存 callee-saved 集合：

| 必须保存/恢复 | 理由 |
|---|---|
| `rsp` | 核心：换栈即换执行流，存入 `prev->ctx.rsp`、从 `next->ctx.rsp` 载入 |
| `rbx, rbp, r12, r13, r14, r15` | callee-saved 通用寄存器，编译器假定跨函数调用不变 |
| 返回地址（栈上的 RIP） | 不单独存：它就在 prev 栈顶，恢复 rsp 后一条 `ret` 即回到 prev 的切换调用点之后 |

| 不保存 | 理由 |
|---|---|
| `rax, rcx, rdx, rsi, rdi, r8–r11` | caller-saved，C 代码在调用切换函数前后本就不指望它们存活 |
| `xmm`/浮点状态 | 本阶段约定内核代码不用浮点/SIMD（实现时 CFLAGS 须加 `-mno-sse -mno-mmx` 类约束，提案，请总协调在 Makefile 侧确认）；用户进程的 FPU 状态保存（XSAVE/FXSAVE）是阶段 2 引入用户代码后的独立课题，切换函数里只留注释标明扩展点，不提前实现 |
| 段寄存器、CR3 | 段在长模式平坦模型下恒定；CR3 不属于「寄存器上下文」，由调度层在切换前后按 §5.3 单独处理，不塞进切换汇编以免职责混杂 |
| `rflags` | 切换点约定在关中断状态下进入，恢复后由各自路径决定何时 `sti`；新任务首次运行的标志位由其启动跳板设定（见 §5.2） |

### 5.2 切换汇编要点（提案函数 `context_switch`）

提案签名：`void context_switch(struct task *prev, struct task *next);`
（或等价的「只传 next、prev 取 current」形式，定稿时二选一。）

汇编骨架须满足的要点（写实现时的核对表，不在此写死全部代码）：

1. 入口顺序：依次 `push rbp, rbx, r12, r13, r14, r15`（顺序一经
   定下，首次运行的伪造栈帧必须按同一顺序排布，两处要在注释里
   互相点名引用）；
2. `mov [prev + ctx.rsp 偏移], rsp` → `mov rsp, [next + ctx.rsp
   偏移]`；
3. 逆序 `pop` 出 next 的六个寄存器，最后 `ret`——next 若是老任务，
   回到它上次调用切换函数的下一条指令；若是新任务，栈顶返回地址
   指向其启动跳板（§5.4）；
4. 全函数不碰中断标志、不碰 CR3、不调用任何 C 函数（切换中途
   栈处于两可状态，任何额外调用都会把水搅浑）；
5. 偏移量纪律：汇编里访问的 `ctx.rsp` 偏移必须与 C 结构一致，
   提案用静态断言（宿主机/编译期 `_Static_assert` 校验
   `offsetof`）把两边钉死，禁止在汇编里手算魔数而不校验。

### 5.3 CR3 的处理位置

按 VMM_DESIGN.md §6.3 的约定放在 C 层 `schedule()` 内、调用
`context_switch` 之前：

```
target_space = next->mm ? next->mm : kernel_master_space;
if (target_space != current_space)
    write_cr3(target_space->pml4_phys);   /* 内核线程借主空间 */
```

好处是切换汇编保持纯粹，且「内核线程借内核主空间」这一约定只有
一处代码。注意写 CR3 会刷 TLB（本阶段未启用 PCID），把它放在
真正切换前而非每次 `schedule()` 无条件执行，是阶段的唯一性能
讲究，其余地方不抠。

### 5.4 新任务的首次运行

- 创建任务时在其内核栈顶手工排一帧「伪造的被切换现场」：
  六个 callee-saved 槽填 0（rbp 可填栈底作帧链终止）、返回地址
  填启动跳板地址；`ctx.rsp` 指向该帧底。第一次被 `context_switch`
  选中时，`pop`+`ret` 自然落入跳板，像它「上次也是在这里被换下」
  一样，切换函数不需要新任务特判。
- 内核线程跳板：开中断（`sti`）→ 调用线程入口函数（参数在创建时
  存入任务结构或跳板约定的寄存器槽，提案存结构字段，避免与
  伪造帧耦合）→ 入口函数若返回，跳板代为调用 `task_exit(0)`，
  不许「返回到切换函数里」——没那种地方可回。
- 用户任务跳板：不直接落 Ring 3，而是先以内核态进入提案的
  `user_task_start` C 函数，完成装载（见 §7）后经 §7.3 的落点
  机制降特权，之后不再回到跳板。

## 6. 与 `syscall.h` 已保留号码的对接

`syscall.h` 已定号码（Linux x86-64 同号）：`clone=56`、
`execve=59`、`exit=60`、`wait4=61`、`kill=62`，另有直接相关的
`getpid=39`、`nanosleep=35`。本节给出每个号在阶段 1 末到阶段 2
的分阶段语义；**总原则：未实现的号返回 `-ENOSYS`，实现了的只做
写明的最小子集并拒绝其余参数组合（`-EINVAL`/`-EOPNOTSUPP`），
绝不静默忽略不认识的 flag**——Linux 程序探到明确错误还能降级，
探到假成功会死得不明不白。

另需先行补齐的地基：**syscall 入口本身尚不存在**。用户态将来经
`syscall` 指令进入（需设置 EFER.SCE、STAR/LSTAR/SFMASK 等 MSR）
或先以 `int 0x80` 作 bring-up 替代——提案：直接做 `syscall`
指令路径，不做 int 0x80 过渡（x86_64 Linux ABI 的正道就是
`syscall`，过渡方案最终要扔）。入口保存用户寄存器、切到当前
任务的 `kernel_stack_top`、按号分发、返回值入 `rax`、负数即
errno（Linux 约定：返回 `-errno`）。此入口属 syscall 层地盘，
本文只声明调度侧的对接点：分发到的进程类 handler 操作的都是
`current` 任务与 §3 的结构。

### 6.1 `exit(60)` —— 最先实现

- 语义：`current` 置 ZOMBIE，记录 `exit_status`（Linux 约定存
  `status << 8` 的 wait 格式由 wait4 侧转换，exit 侧只存原始码，
  二选一须在实现时写死一处，提案 exit 存原始码、wait4 组装）；
  释放其用户地址空间与数据页（经 VMM 接口，先切走 CR3 再销毁，
  遵守 VMM_DESIGN.md §6.3 的销毁前置条件）；唤醒在 wait 它的
  父任务；最后调用 `schedule()` 且**永不返回**（函数标
  `_Noreturn` 语义，返回即 bug）。
- 子进程善后：退出者的子进程过继给 init（parent_tid 改 1），
  init 有义务周期性 wait 回收，保证无僵尸堆积——这是 init 的
  合同之一，写在 §7。
- 内核线程退出复用同一路径（`mm==NULL` 时跳过地址空间释放），
  idle（0 号）禁止退出，调用即断言失败。
- `exit_group(231)` 未在现 `syscall.h` 中：glibc 程序实际调用的
  多是 exit_group。**提案：请总协调评估在 syscall.h 补 231 号**
  （属接口变更，本文只提案不擅改）；补上前，静态/裸 syscall 的
  测试程序可先用 60 验证路径。

### 6.2 `clone(56)` —— 阶段 2 首发，阶段 1 只留骨架

- 阶段 1 末：handler 存在但只接受「fork 式」调用的探测性实现
  或直接 `-ENOSYS`，二者取一由总协调定；本文推荐先 `-ENOSYS`，
  等 VMM 用户空间与页拷贝就绪再开，半成品 fork 比不实现更危险。
- 阶段 2 最小子集（fork 语义）：flags 只接受 `SIGCHLD(17)` 与 0，
  其余位（CLONE_VM/VFORK/THREAD 等）返回 `-EINVAL`；实现路径：
  新建 task → `vmm_create_space` → 逐页拷贝父空间用户半区数据
  （先做全拷贝，COW 是后续优化，不在本阶段承诺）→ 复制 §5.1
  的父任务被 trap 现场，使子任务从 syscall 返回点「复活」且
  `rax=0`，父侧 `rax=子 tid` → 子任务入运行队列队尾。
- 明确差异并写进注释：Linux 的 clone 还涉及传入的栈指针、TLS
  （配合 `arch_prctl=158`，已保留号）等，本子集一律不处理，
  传入非空 child_stack 即 `-EINVAL`，不假装支持。

### 6.3 `wait4(61)`

- 最小子集：`pid > 0` 等指定子进程；`pid == -1` 等任意子进程；
  `options` 只支持 0 与 `WNOHANG(1)`；`rusage` 传非空时填零
  结构体（或直接接受 NULL， glibc 包装通常传 NULL/有效指针，
  填零比 `-EFAULT` 更兼容，提案填零）。
- 行为：有 ZOMBIE 子进程 → 组装 status、回收其 task 结构与
  内核栈、返回其 pid；无子进程 → `-ECHILD(10)`；有子进程但都没
  退出且无 WNOHANG → 当前任务 BLOCKED 睡在「等子进程退出」条件
  上，被 §6.1 的 exit 唤醒后重试；WNOHANG 则返回 0。
- 实现 simplification（提案，写明取舍）：等待关系不建专用队列，
  父任务阻塞时由 exit 路径按 parent_tid 全表扫描唤醒——任务数
  小时正确且代码最少，全表扫描点集中在 exit 一处。

### 6.4 `kill(62)`

- 本阶段语义（信号机制未建之前的最小可用集）：`sig` 只接受
  `SIGKILL(9)` 与 `SIGTERM(15)`，效果是令目标任务按 §6.1 路径
  终止（状态标记为「被杀」，exit_status 按信号格式记录，供
  wait4 组装出 `WIFSIGNALED` 形态）；`SIGCONT/SIGSTOP` 及其余
  信号返回 `-EINVAL`；目标不存在返回 `-ESRCH(3)`；`pid==0/-1`
  的进程组语义不支持，返回 `-EINVAL`。
- 目标是内核线程或 idle 时拒绝（`-EPERM`），不许 kill 掉内核
  自己的执行流；给自己发 SIGKILL 等价于 exit（走同一终止路径）。
- 注释中必须标注：这是「终止请求」而非完整信号递送——目标任务
  若在不可中断的内核临界区，要等它回到可调度点才真正终止
  （提案以任务上的 `pending_kill` 标记 + 调度点检查实现，
  而不是从 kill 调用里强行切换对方的上下文）。

### 6.5 `getpid(39)` 与 `nanosleep(35)`

- `getpid`：返回 `current->tid`，一行实现，随 syscall 入口第一批
  落地，用作入口打通的冒烟用例。
- `nanosleep`：依赖 §4.2 第二步的 tick 基础设施：把时长换算为
  tick 数（向上取整），当前任务 BLOCKED 并登记到期 tick，tick
  中断到期唤醒；被 kill 标记打断时返回 `-EINTR(4)` 并按 Linux
  约定回填 `rem`。协作式阶段（无 tick）此号返回 `-ENOSYS`，
  不许用忙等假装睡过。

## 7. init：第一个用户进程的启动路径

### 7.1 前置条件与一个接口缺口

启动 init 需要：VMM 用户空间、把可执行映像放进该空间的手段、
Ring 3 落点机制。前两件中藏着一个现接口缺口，必须先报总协调
裁决，本文只提案：

- **`boot.h` 没有 initrd/模块字段**，内核无从得知 init 程序在哪。
  候选：(a) 扩展 boot 信息（加一个「引导模块」物理地址+长度
  字段，改 boot.h，须总协调批准并与 Bootloader 侧同步）；
  (b) 过渡方案：把一份静态链接的极小 init 以二进制形式链接进
  内核映像（随内核一起被加载），内核从自身映像里取其字节。
  **提案：阶段 1 用 (b) 打通路径，阶段 2 随文件系统/ramdisk 改
  (a) 或正规模的初始内存盘。** (b) 的好处是不动已锁定接口、
  不依赖 Bootloader 新功能；坏处是换 init 要重编内核——
  bring-up 期可接受，写明为过渡，不许沉淀成正式方案。

### 7.2 启动顺序（`kmain` 尾部，提案）

```
pmm_init -> vmm_init -> sched_init:
    创建 idle 任务（tid 0，mm=NULL，入口为 hlt 循环）
    创建 init 任务（tid 1，此时仅是任务结构 + 内核栈，
                    mm 暂空，入口指向 §5.4 的用户任务跳板）
    （里程碑早期此处可替换为两个打印型内核线程先验切换，见 §8）
  -> 首次 schedule() 选中 init 任务 -> context_switch 落入跳板
```

### 7.3 init 任务跳板内做的事（仍在内核态，`current == init`）

1. `vmm_create_space` 得新空间并记入 `init->mm`；
2. 解析内嵌映像：**先支持静态 ELF64**（程序头逐个 `PT_LOAD`：
   PMM 申请数据页 → 按段拷贝文件字节、清零 bss 部分 → 按段权限
   `vmm_map` 进用户低半区）。ELF 加载器本体属阶段 2 地盘，此处
   只需要它对「一个静态、无动态链接器、无重定位花样」的最小
   子集，复杂 ELF（动态链接、PIE 的完整语义）不本阶段承诺；
   在 ELF 子集就绪前，可先用「裸扁平二进制 + 固定入口地址」
   作更前一步的冒烟（§8 里程碑 M3），但正式 init 走 ELF。
3. 建用户栈：在用户空间高位（如栈顶提案 `0x7FFFFFFFF000`，
   向下增长）映射若干页（提案 4 页 + guard 页），按 Linux 初始
   栈布局压入 argc/argv/envp 与 auxv 的最小集合（`AT_PAGESZ`、
   `AT_PHDR` 等动态程序才需要的项，静态 init 可给最小集，
   少给的后果是部分 libc 启动代码不干活——init 应为静态且尽量
   裸 syscall 编写，此约束写入 userland 侧任务说明）；
4. 设置落点：把 `user_ip = ELF 入口`、`user_sp = 栈顶` 写入
   任务结构；
5. 降特权落点：构造 iret 帧（用户 CS/SS、RFLAGS 置 IF=1、
   RIP=user_ip、RSP=user_sp）执行 `iretq`，或经 syscall 机制
   的 `sysret` 对偶路径——**提案用 `iretq`**：它不依赖 MSR
   配置状态、帧格式直观，bring-up 期少一类「MSR 设错」的故障；
   性能差异在本阶段无关紧要；
6. init 在 Ring 3 的第一件事应是可观测的：向 fd 1 `write` 一行
   问候（经 §6 的 syscall 入口回到内核、由串口打出），随后进入
   其正式职责：按服务器版里程碑，init 拉起 Shell 进程
   （`clone`+`execve`，依赖 §6.2 与 VFS/ELF 的 exec 路径；
   在此之前，init 自带一个读串口、回显、识别两三条内建命令的
   极简循环作过渡，使「Shell 能敲命令」的里程碑可以先以
   init 内建形态点亮，再拆出独立 Shell 进程）。

### 7.4 init 的长期合同（进程语义的地基）

- init 永不退出：它 exit 则内核无父可托、无根可守，实现上
  init 调用 exit 时内核直接 panic（串口打印 + halt），与 Linux
  的 "Attempted to kill init" 对应；
- init 负责回收过继来的孤儿僵尸（§6.1），其主循环须包含
  周期性 `wait4(-1, WNOHANG)`；
- init 是 1 号，`parent_tid = 0`。

## 8. 分步里程碑（每步可验证）

| 步 | 内容 | 验证方式（通过标准） |
|---|---|---|
| M0 | 调度纯逻辑宿主机单测：运行队列入/出、状态迁移、RR 挑选顺序、`task` 表查找（队列/状态机代码与切换汇编分离，逻辑层可 hosted 编译，做法同 PMM/VMM） | `tests/test_sched.c`（提案）全绿：含「三任务轮转顺序」「阻塞任务被跳过、唤醒后回队尾」「ZOMBIE 不被挑中」等断言 |
| M1 | 协作式内核线程：sched_init + context_switch + 两个打印线程各打一行后 yield，交替若干轮后由计数触发收尾 | 开机串口日志严格交替（如 A/B 各 10 行无丢无重），`make check` 绿；此步验透伪造栈帧与 callee-saved 保存 |
| M2 | 定时器抢占：IDT+PIC+PIT 100 Hz 落地，线程改为死循环计数不主动 yield，靠 tick 轮转；另加一个 nanosleep 睡眠任务 | 两忙等线程的计数增长大致交替（串口周期采样）；睡眠任务按时醒来打印；关中断临界区无队列损坏迹象 |
| M3 | Ring 3 冒烟：一个任务装载裸扁平二进制到用户空间，iretq 落 Ring 3，执行 `getpid` 与 `write` 两个 syscall 后 `exit` | 串口收到用户态写出的问候行与正确 pid；父（内核侧监护线程/init 骨架）经 wait 路径回收到其退出码 |
| M4 | init 正式上岗：内嵌静态 ELF init 按 §7 路径启动，init 内建极简命令循环读串口 | 串口可交互：敲 `help`/`ps`（列全表任务）/`exit` 等内建命令有正确回应；kill 一个睡眠中的子任务后 ps 显示其消失且无僵尸残留 |
| M5 | fork/exec 拆分：clone 最小子集 + execve（依赖 VFS/ELF 侧里程碑）打通，init 拉起独立 Shell 进程 | Shell 作为独立 pid 存在，命令退出后回到 Shell 提示符；连续执行多条命令无内存泄漏（PMM free 页数在每轮前后对账，差值归零） |

每步之间不许跳步合并提交：M1 的切换 bug 若混进 M2 的中断代码，
将无从分辨是栈帧错还是 IRQ 现场错——这是排里程碑顺序的主要理由。

## 9. 风险清单

1. **最大风险：地基缺口集中在「中断」一件事上**。IDT、PIC、
   定时器、#PF 处理目前全不存在，而抢占调度、nanosleep、
   VMM 的故障定位、用户态异常隔离都压在它上面。它一旦延期，
   §8 只能停在 M1（协作式），整个阶段 1 的「Shell 能跑」会因
   无抢占而质量打折。建议总协调把 IDT+PIC+PIT 作为独立小步
   排在 M1 之后、M2 之前优先落地（其归属地盘也需总协调指派）。
2. 伪造初始栈帧与切换汇编的 pop 顺序不一致，是这类内核最经典
   的首启崩溃点，且崩时无任何输出。缓解：§5.2 的顺序互引注释
   + offsetof 静态断言 + M1 的交替打印作为硬验收，不接受
   「看起来对」。
3. FPU/SIMD 状态暂不保存（§5.1）：若某个用户程序用了 SSE
   （现代编译器默认会），其寄存器会在任务切换时被别的任务
   污染，症状是偶发数据错误而非崩溃，极难查。本阶段以
   「init/Shell 为受控自研程序、不启用 SIMD」规避；阶段 2
   面向任意 Linux 程序前，XSAVE 区必须进任务结构，此条记入
   阶段 2 的准入条件，不得遗忘。
4. 内核栈溢出在 guard 页落地前是静默踩内存问题；guard 页
   依赖 VMM 能按页设不可访问，排在 VMM 之后天然满足，但 M1
   若在 VMM 完成前先行（只为验切换），须明示该阶段无 guard、
   线程代码保持浅调用链。
5. clone 全拷贝（非 COW）在大进程 fork 时内存与耗时陡增；
   服务器里程碑阶段进程都很小，可接受，但设计上页拷贝循环
   要写成「将来可换成 COW 标记」的形状（逐页、经 VMM 接口），
   不许用 memcpy 整段绕过 VMM。
6. kill 的「标记 + 调度点检查」意味着处于长临界区的任务无法
   被及时杀死；本阶段临界区都很短，可接受，但任何新增的长
   关中断区段都要在评审时自问是否会让 kill/抢占失效。
