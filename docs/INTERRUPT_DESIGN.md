## 1. 目标与非目标

### 1.1 目标

1. 一张完整的 256 项 IDT：0–31 号异常有明确归宿，IRQ 有明确向量
   区间，未启用的向量落到「转储并停机」的安全默认，而不是落到
   随机地址或静默复位。
2. 时钟节拍成为调度的时间基准：100 Hz tick 驱动时间片、睡眠到期
   与运行时间统计，使 SCHED_DESIGN 的抢占从 M1 协作式升级为真抢占。
3. 任何内核故障（尤其 #PF）都留下一份串口转储再死，而不是三重
   故障静默重启——无头服务器场景下，串口日志是唯一的黑匣子。
4. 为两个后续里程碑预埋正确形状：控制台输入（IRQ1 键盘）与
   Ring 3（中断从用户态进来时的栈切换，见 §8）。

### 1.2 非目标

- 不做 APIC/LAPIC/IOAPIC 与 MSI：8259 PIC 足够单核 bring-up；
  迁移到 LAPIC 的时机是上 SMP 之前，届时 PIT 让位给 LAPIC timer，
  本文 §6 的 tick 语义不变、只换信号源（接口隔离已做到：调度只
  认识 `sched_tick()`，不认识 PIT）。
- 不做中断线程化、不做软中断/tasklet 类机制：handler 里只做
  「记账、置标志、唤醒」，重活留给被唤醒的任务——这是「快与干净」
  在中断层的具体含义，见 §5.3 的 tick 工作清单铁律。
- 不做 NMI 看门狗、机器检查（#MC）的恢复语义：#MC 向量照常装
  转储桩，策略是打印后停机，不假装能恢复。
- 不在本阶段引入每 CPU 数据结构：单核，GS 基址的用途留给
  SYSCALL_DESIGN.md 的 syscall 入口，两文共用同一份 GDT/TSS
  规划（§8），不在本文另起一套。

## 2. IDT 布局

### 2.1 向量分配

IDT 共 256 项，每项 16 字节（64 位门描述符），整表 4 KiB。
向量空间按下表一次划清，未列出的向量一律指向默认桩（§2.3）：

| 向量 | 来源 | 本阶段处理 |
|---|---|---|
| 0–31（0x00–0x1F） | CPU 异常（架构保留） | 逐项装异常桩，统一转储后停机；#PF(14) 特殊，见 §7 |
| 32（0x20） | PIC 主片 IRQ0（PIT 时钟） | 唯一放行的 IRQ；`irq0_stub` → `irq0_handler()` → `sched_tick()` |
| 33（0x21） | IRQ1（PS/2 键盘） | 本阶段掩码；控制台输入里程碑启用，规划见 §4.3 |
| 34（0x22） | IRQ2（级联脚） | 永远掩码，永不单独放行（从片经此脚级联，放行它无意义） |
| 35–39（0x23–0x27） | IRQ3–IRQ7（串口/并口等） | 掩码。串口驱动现为轮询发送，不用 IRQ4；接收中断化是控制台阶段的事，与 IRQ1 一并评估 |
| 40–47（0x28–0x2F） | PIC 从片 IRQ8–IRQ15 | 全掩码（RTC 在 IRQ8 上：将来需要墙钟时间可在此启用周期中断或读 CMOS，本阶段不用） |
| 48–255（0x30–0xFF） | 无硬件来源 | 装默认桩。特别说明：**0x80 不用作 syscall 入口**（理由见 SYSCALL_DESIGN.md §2，int 0x80 在 64 位 Linux 上是 32 位兼容表，借用必乱套），因此 0x80 与其它空向量同等对待，不设 DPL=3 的门 |

### 2.2 门的属性：清一色中断门

- 类型属性统一 `0x8E`：Present、DPL=0、64 位中断门（interrupt
  gate）。中断门在进入时硬件自动清 IF——这正是我们要的：任何
  handler 入口即处于关中断状态，不必在桩里先 `cli`，且天然防
  止同源中断重入（§5.4）。
- 不用陷阱门（trap gate，0x8F）：陷阱门不清 IF，会让 handler 在
  开中断下运行，临界区纪律立刻复杂化。本阶段没有任何 handler
  需要「进来先开着中断」的语义；将来某设备 handler 若嫌关中断
  太久，正确做法是 handler 内记账后尽早 EOI+开中断，而不是换门。
- DPL 一律 0：用户态不得用 `int n` 主动跳进任何门。syscall 不走
  IDT（走 MSR 入口），所以本表不需要任何 DPL=3 的例外，这让
  「Ring 3 能到达的内核入口有且只有一个」成为可审计的事实。
- 段选择子统一为当前代码段 `0x08`。**耦合警告**：此值取自现行
  stub GDT（code64=0x08、data=0x10）；将来内核自有 GDT 落地
  （§8）或 UEFI 引导链带来不同 GDT 时，这个常量必须随之迁移。
  实现上应保持它只有一处定义、注释点名依赖，禁止散落魔数。

### 2.3 桩的分工：异常桩与 IRQ 桩是两类

- **异常桩（0–31）**：每向量一个小桩，只做「压向量号 → 跳公共
  入口」。公共入口把当时的栈指针交给 C 层 `exception_handler()`，
  由它按向量号解出错误码/RIP（有错误码的向量集合是架构定的：
  8、10–14、17、21、29、30），打印后停机、永不返回。因此异常
  桩不需要保存通用寄存器——现场不需要恢复，保存了也是白保存，
  这是刻意的瘦身，不是疏忽。其推论：若将来 #PF 要走「终止当前
  用户任务而非整机停机」的恢复路径（§7.3 第二阶段），#PF 桩须
  升级为保存全部寄存器的独立桩，届时单独改它，不动其余异常桩。
- **IRQ0 桩**：保存 caller-saved 集（rax、rcx、rdx、rsi、rdi、
  r8–r11，共 9 个）后调用 C handler，恢复后 `iretq`。保存集的
  依据：handler 是普通 C 函数，SysV 约定下编译器只保证
  callee-saved 由被调用方保护；被打断代码的 caller-saved 寄存器
  必须由桩兜住。callee-saved 不在桩里保存——handler 的 C 代码
  会按约定自己保存，而抢占切换时的那一份由 `context_switch()`
  在被换出任务的栈上保存，两处分工不重叠。
  对齐纪律：9 次 push 加上硬件压入的 5 字中断帧（RIP/CS/RFLAGS/
  RSP/SS；同特权级时 RSP/SS 不压入，实际为 3 字），桩在 `call`
  handler 前的栈对齐须按实际情形算清并注释——已在实现中注明
  （9 个 push 与硬件帧配合使 C 调用点满足 16 字节对齐），后续
  改动 push 个数时必须同步重算，不许凭感觉增减。
- **默认桩（未用向量）**：与异常桩共用转储路径，向量号用一个
  约定值（如压 `0x100 + 向量` 或单设「unexpected interrupt」
  打印）以便区分「真异常」与「不该来的中断来了」。触发它说明
  有未掩码的中断源或 IDT 装错，停机保住现场比 `iretq` 假装
  没事更符合 bring-up 阶段的利益。

## 3. 异常策略分工

异常是同步事件、无 EOI、不可「处理完继续」——本阶段策略统一为
**转储 + 停机**，但转储内容按向量分三档，避免一刀切漏信息：

| 档 | 向量 | 转储内容 |
|---|---|---|
| 通用档 | 0 #DE、6 #UD、13 #GP、16 #MF、19 #XM 等 | 向量号、错误码（有则）、RIP |
| 页故障档 | 14 #PF | 通用档 + CR2 + 错误码逐位解码 + 当前任务 + 页表走查结果（§7，本设计的重点） |
| 致命档 | 8 #DF | 能打多少打多少：#DF 意味着前一个异常的处理本身又出错，栈可能已不可信；打完停机。真正的防护靠 §8 的 IST 独立栈（后续步），不是靠 handler 写得壮 |

补充规则：

- **#UD 要特别点名**：内核编译已禁用 SSE/MMX（Makefile 的
  `-mno-sse -mno-mmx`），若在内核里撞上 #UD，多半是执行了
  数据或跳错了地址，转储时建议额外打印 RIP 处起 8 字节内容
  （提案），能一眼区分「跳进数据」与「真非法指令」。
- 异常发生在中断关闭的临界区（如 `sched_schedule()` 的
  pushf/cli 区段）时，转储路径只做轮询串口输出——串口驱动是
  纯端口 I/O、不睡眠、不拿任何会被临界区持有的资源，这是它
  能当黑匣子的前提；任何让串口输出路径将来依赖中断/锁的
  改动都会破坏这条，须在评审时拦下。
- 用户态异常的分化（终止任务而非停机）不在本阶段：当前所有
  执行流都在 Ring 0，异常即内核 bug，停机是对的。分化点与
  SYSCALL_DESIGN 的 Ring 3 里程碑绑定，见 §7.3。

## 4. PIC 重映射

### 4.1 为什么必须重映射

两片 8259 上电默认向量基址在 0x08 与 0x70：主片的 0x08–0x0F 与
CPU 异常向量（#DF=8、#TS=10……）正面重叠，不重映射则第一个
时钟中断就会被当成双重故障。因此 `interrupts_init()` 在装完
IDT 后立即重映射：主片基址 `0x20`、从片基址 `0x28`，恰好接在
异常区之后、互不重叠（§2.1 表即以此为准）。

### 4.2 初始化序列（契约，按实现写明以备复查）

1. 保存两侧原掩码（bring-up 礼仪；本阶段后面统一全掩码，保存
   值暂不恢复，但序列保留完整形状，将来 UEFI 链交接时不至于
   丢失固件可能设置的掩码上下文）；
2. ICW1=`0x11`（初始化、边沿触发、级联、需要 ICW4）发往主片
   命令口 `0x20` 与从片命令口 `0xA0`，每步之间 `io_wait()`
   （写 0x80 诊断口）留硬件 settling 时间；
3. ICW2：主片 `0x20`、从片 `0x28`（向量基址）；
4. ICW3：主片 `0x04`（从片挂在 IRQ2）、从片 `0x02`（级联身份）；
5. ICW4=`0x01`（8086 模式）；
6. 收尾掩码：主从两片数据口都写 `0xFF`——**重映射完成 ≠ 允许
   中断**。放行是另一个动作，只能由各设备自己的启动函数逐个
   做（下一条），这样任何时刻「哪个中断源是活的」都有一行
   代码可指。

### 4.3 放行纪律与后续 IRQ 的归属

- IRQ0：由 `timer_start()` 单独放行——写主片掩码 `0xFE`
  （只清 bit0；注意 IRQ2 级联位 bit2 此时仍为 1，即从片整体
  仍被屏蔽，与「从片全掩码」叠加，从片不可能有来源）。
- IRQ1（键盘）：控制台输入里程碑放行，放行点写在键盘驱动的
  init 里，同时在本文 §2.1 的规划行转正。届时主片掩码变为
  `0xFC`。纪律：不许在 `interrupts_init()` 里「顺手」先放行。
- 其余 IRQ 在可预见的里程碑内保持掩码；每新增一个，先在此表
  登记向量、来源、handler 归属，再写放行代码。

### 4.4 EOI 规则

- 主片 IRQ（0–7）：只向主片命令口发 EOI（`0x20`）。
- 从片 IRQ（8–15）：先向从片、再向主片各发一次 EOI（本阶段
  无从片来源，此条是给将来启用 RTC 等来源的预登记规则）。
- **IRQ0 的 EOI 时机**：`irq0_handler()` 在调用 `sched_tick()`
  **之前**先发 EOI。理由是硬性的：`sched_tick()` 可能触发
  `sched_schedule()` 把当前任务换出，换回已是若干时间片之后；
  若 EOI 等在切换之后，中断在 PIC 侧一直处于 in-service，
  后续 IRQ0 全被堵住，时钟在「第一次抢占」后就死了。先 EOI
  不等于允许嵌套：中断门进门已清 IF，handler 全程 IF=0，
  下一个 tick 只能在 `iretq` 或被换入任务恢复其 RFLAGS 后才
  可能进来（§5.4）。
- 伪中断（spurious IRQ7/IRQ15）：现阶段 IRQ7/15 都掩码，不会
  发生；将来放行主片其它线后，IRQ7 handler 须先读主片 ISR
  （OCW3）确认 in-service 位，为伪中断时**不发 EOI** 直接
  返回；IRQ15 的伪中断则只给主片发 EOI、不给从片。此规则
  先登记在此，启用相应 IRQ 时一并实现，不提前写代码。

## 5. 与调度的抢占衔接

### 5.1 tick 里做什么：`sched_tick()` 的工作清单

`irq0_handler()` 的构成固定为两步：发 EOI → 调 `sched_tick()`。
`sched_tick()` 在关中断上下文（中断门保证 IF=0）中依次做：

1. **推进全局节拍**：`uptime_ticks++`（u64，100 Hz 下溢出需
   5.8 亿年，不处理）；`sched_uptime_ticks()` 供 nanosleep 换算
   与将来 uptime 类接口读取。
2. **唤醒到期睡眠者**：扫描任务池（上限 32，全扫成本可忽略），
   `wake_tick != 0 && wake_tick <= uptime` 的 BLOCKED 任务清
   `wake_tick` 并 `sched_wake()` 入运行队列尾。睡眠入口
   `sched_sleep_ticks(n)` 的语义是「至少睡 n 个 tick」：到期
   时刻 = 调用时 uptime + n（n=0 时按 1 处理还是立即返回，
   在 nanosleep 落地时按 Linux 语义定，提案：0 直接 yield）。
3. **给当前任务记账**：`current->total_ticks++`；
   `current->timeslice_left--`（idle 不记账、不扣片——idle 的
   调度走下一条的快路径，扣它没意义）。
4. **判定是否重调度**（满足其一即调 `sched_schedule()`）：
   - 当前任务时间片耗尽（`timeslice_left == 0`）；
   - 当前是 idle 且运行队列非空（idle 让位不等时间片，这是
     睡眠/唤醒延迟的下限保证：唤醒后最迟下一个 tick 就能跑，
     实际在唤醒发生的 tick 内即可被调度）。
   `sched_schedule()` 内部会把仍可运行的当前任务排回队尾并
   重置被选任务的 `timeslice_left = YOUSJ_SCHED_SLICE_TICKS`
   （=5，即 50 ms，SCHED_DESIGN §4.2 已定）。

### 5.2 切换时机：就在 IRQ 上下文里切，不设「待办标志」

本设计采用 Linux 早期与多数教学内核的分工：**判定与切换都在
tick 内完成**，不采「置 need_resched 标志、等返回用户态前再切」
的两段式，理由：

- 当前全部执行流是内核线程，所谓「返回点」只有中断返回这一条
  路，被换出任务的中断帧就压在它自己的内核栈上，`context_switch()`
  换栈后，新任务从它自己的中断帧/伪造帧继续，旧任务将来被换回时
  从 `sched_schedule()` 的调用点返回、穿过它那一侧的
  `irq0_stub` 恢复段与 `iretq` 回到被打断处——整条链只依赖
  「每任务一栈、中断帧随栈走」这一条不变量，不需要额外的
  标志位状态机，干净。
- 两段式（标志位）的收益在「中断可能落在内核不可抢占区」时才
  显现，而本内核的不可抢占区就是关中断区段：IF=0 时 tick
  根本进不来，硬件已经替我们做了延迟判定。等将来出现「长
  时间开中断跑的内核路径需要避让」时再议，不预建。

### 5.3 tick 的工作量铁律（快与干净的落地）

- tick 里禁止串口打印、禁止任何可能阻塞/睡眠的操作、禁止
  分配内存（唤醒只动链表）。tick 的成本必须 O(任务数) 且
  常数小：100 Hz 下每秒 100 次，任何一次超标都会变成全系统
  的固定税。
- 设备 handler 将来一律照此办理：只清硬件状态、记账、唤醒
  等待者，其余工作留给任务上下文。评审任何新 handler 时以
  此条为据。

### 5.4 防重入与临界区纪律

- IRQ0 handler 全程 IF=0（中断门语义），不存在 tick 重入
  `sched_tick()` 的可能；`sched_tick()` 及其调用的队列操作
  以此为前提，不再各自 cli/sti——前提必须写在函数注释里
  （已在 interrupts.h/sched.h 的契约注释中体现）。
- `sched_schedule()` 自身的 pushf/cli → popf 纪律解决的是
  **非中断上下文**调用它时的原子性（协作式 yield、阻塞、
  退出路径），与 tick 路径互补：tick 进来时 IF 本就是 0，
  popf 恢复的也是该次调用保存的 0，不会把中断错误地打开。
  关键不变量一句话：**谁保存的 RFLAGS 谁恢复，且保存在自己
  任务的栈帧里**——任务在 `sched_schedule()` 中途被换出，
  恢复的是它自己的那一份，不存在全局标志串扰。
- idle 的等待姿势（提案）：idle 任务的主循环应采用
  `sti; hlt` 后接 `sched_schedule()` 的形态——`sti` 的
  「下一条指令后才生效」语义保证 hlt 前不会漏掉刚到的 tick，
  避免「队列刚有活、idle 却睡死过去」的竞态。kmain 现在的
  `cli; hlt` 是终局停机姿势，不得挪作 idle 循环。

### 5.5 从 Ring 0 抢占到 Ring 3 抢占的衔接点（预告）

用户任务出现后（M3+），tick 打断的可能是 Ring 3 代码：CPU
经 TSS.rsp0 切到当前任务的内核栈（§8），中断帧含用户
RIP/CS/RFLAGS/RSP/SS 五字，之后的桩、`sched_tick()`、切换
机制与 Ring 0情形完全同构——这正是把入口设计成「帧随栈走」
的回报。返回用户态前由 SYSCALL_DESIGN 的出口路径顺带检查
「在 tick 中已被标记待终止（kill）」类事项，本文不展开。

## 6. PIT 100 Hz 配置

- 通道与模式：PIT 通道 0，命令字 `0x36`（通道 0、 lobyte/
  hibyte 两段写、模式 3 方波、binary 计数）写入命令口
  `0x43`，分频值写入数据口 `0x40`。
- 分频值：基准频率 1,193,182 Hz ÷ 100 = 11,931（0x2E9B），
  实际频率 100.006 Hz，误差 0.006%，对 10 ms 级调度与睡眠
  无意义，不做校正。分频值只以 `PIT_BASE_HZ / YOUSJ_HZ`
  形式出现（已实现），`YOUSJ_HZ` 是唯一旋钮。
- 为什么是 PIT 而非其它源：
  - LAPIC timer：需先经 ACPI/APIC 发现与校准（还要借 PIT
    校准一圈），是 SMP 里程碑的配套件，现在上等于把调度
    绑死在 ACPI 解析上；
  - HPET：同样要解析 ACPI 表，且寄存器在 MMIO，需 VMM 的
    内核映射先就位（CR3 切换尚未落地）；
  - RTC 周期中断：频率是 2 的幂（1024/512…），凑不出整
    100 Hz，且与墙钟寄存器共用一套读写礼仪，易互相干扰。
  PIT 是唯一「三个端口写完就走」的源，符合先行阶段的选型。
- PIT 只提供节拍、不提供墙钟：系统时间（年月日）将来由 RTC
  在启动时读一次 + tick 累加维护，不归本设计管。`uptime`
  语义（单调递增的 tick 数）与墙钟严格分开，nanosleep 与
  将来的 `clock_gettime(CLOCK_MONOTONIC)` 消费前者。

## 7. #PF 串口转储探针：从「有转储」到「能定位」

### 7.1 定位

VMM_DESIGN §9 与 SCHED_DESIGN §9 共同点名的最大风险是：
页表/地址空间一旦出错，故障表现为无输出的静默崩溃。现实现
的 `exception_handler()` 已做到第一层：任何异常都打印
「向量号 + 错误码 + RIP」再停机。本节把 #PF 这一档补成能
直接定位的探针，并给出可自动验收的落地路径——这是它被称作
「探针」而不只是「日志」的原因。

### 7.2 #PF 转储的完整字段（提案）

`exception_handler()` 对向量 14 增加以下输出（其余向量维持
现行三项）：

1. **CR2**：出错的线性地址——#PF 的第一证据，必须在 handler
   入口第一时间读走（读 CR2 的小汇编助手为**提案**新增，置于
   arch 层）。理由：handler 自身若再触发缺页（比如转储代码
   踩到坏映射），CR2 会被覆盖，原案发现场即灭失。
2. **错误码逐位解码**（打印短串，如 `P=0 W=1 U=0 RSVD=0 I/D=0`）：
   区分 不存在/保护、读/写、内核/用户、取指——四种组合对应
   四类完全不同的 bug（空指针、写只读、用户踩内核、跳飞），
   解码放在打印侧而不是让人对着十六进制心算。
3. **当前上下文**：当前任务名与 tid（`sched_current()`）、
   当前 CR3（读回值）、出错地址所属区间判定（用户低半区 /
   HHDM / 内核映像区 / 非 canonical，按 VMM_DESIGN §3 的
   常量表对照）。
4. **页表走查交叉验证**：用 `vmm_translate()` 对 CR2 在当前
   地址空间（以及必要时内核主空间）做只查不改的走查，打印
   「第几级断链」或「已映射、物理页=…、抽象标志=…」。转储
   由此能区分两类高频情形：映射根本没建（建表 bug）与
   映射在但权限不对（标志 bug）——没有这一项，#PF 日志只能
   告诉你「死了」，有这一项才告诉你「死在哪一级」。

转储全程只用轮询串口与只读走查，不分配、不改任何状态：
它是观察者，不能成为第二个故障源。

### 7.3 策略分阶段

- **现阶段（全 Ring 0）**：#PF = 内核 bug，转储后停机，无例外。
- **M3 之后（有用户任务）**：按错误码 U 位分化——U=1（用户态
  出错）走「转储一行摘要 → 终止当前任务（按 SCHED_DESIGN
  §6.1 的 exit 路径，退出码体现被故障杀死）→ 调度下一个」，
  整机不停；U=0 仍停机。此分化要求 #PF 桩升级为全寄存器
  保存桩（§2.3 已预告），且终止路径不得在中断上下文直接
  释放地址空间（遵守 VMM_DESIGN §6.3 的销毁顺序：先切走
  CR3 再销毁）——实现上提案：#PF handler 对 U=1 只做
  「记录故障信息到当前任务 + 置待终止标志」，真正的退出
  清理在返回用户态前的检查点由任务自己执行，与 kill 的
  延迟终止机制共用一条路，避免在异常栈上做重活。

### 7.4 可验收的探针落地路径

分两步，每步都有机器可判的通过标准（沿用 `make run` 看串口
输出的现行验收方式）：

- **探针 A（预期停机型，先落地）**：kmain 在 M2 自检段末尾，
  在一个显式开关下（提案：仅当 boot cmdline 或编译开关启用）
  主动解引用一个明知未映射的地址（如 HHDM 区内一个从未建
  映射的高地址，或用户区 `0x0000DEAD00000000` 量级地址——
  选址须避开现有全部映射并在注释里写明），预期串口出现
  §7.2 的完整 #PF 转储后停机。验收：转储中的 CR2 与选址
  逐字一致、解码位与人为构造的访问方式（读/写）一致、
  走查结果报出正确的断链级数。
- **探针 B（可恢复型，随 M3 落地）**：探针代码改为一段专用
  汇编小片段：在已知地址标号处故意访问未映射页，#PF
  handler 若发现 RIP 恰等于该标号且处于探针武装状态，则
  不停机，改为修正保存的 RIP 到恢复标号、清武装标志、
  打印一行「probe recovered」后返回——被探针代码验证
  「已恢复」并继续跑完后续自检。此步的价值是验证 §7.3 的
  「 handler 能改道执行流」机制，为用户任务的故障终止路径
  预演；RIP 精确匹配是硬条件，任何其它 RIP 的 #PF 绝不
  允许走恢复分支，防止把真 bug 吞掉。

## 8. 前置件：内核自有 GDT 与 TSS（与 SYSCALL_DESIGN 共用）

现行 GDT 借自启动 stub（仅代码/数据两段、无 TSS）。中断层
自身在两个点上迟早要撞到它的边界，须排期（提案，归属请
总协调定，建议随 M3 一并落地，一次做对）：

1. **TSS.rsp0**：Ring 3 任务被中断/异常打断时，CPU 自动从
   TSS.rsp0 取内核栈。没有 TSS，用户态一开中断就无栈可用。
   纪律：`sched_schedule()` 每次切换后把 TSS.rsp0 更新为
   新任务的 `kernel_stack_top`（单核下 TSS 只有一份，更新点
   只有一处，与 CR3 的更新点并排）。
2. **IST 独立栈**：#DF（与将来的 NMI/#MC）应经 TSS 的 IST
   机制落到一张专用小栈上，避免「内核栈已爆 → #PF 推不进
   帧 → #DF 再推不进 → 三重故障复位」的哑火链。本阶段
   IDT 里 IST 字段为 0（现实现）；提案在 GDT/TSS 落地时给
   #DF 分配 IST1（4 KiB 专用栈），#PF 不用 IST（它需要在
   出错任务自己的栈上处理 §7.3 的终止路径）。
3. **GDT 段布局**须同时满足 syscall 的 STAR  arithmetic
   （内核代码/数据、用户数据/代码的相对位置有硬件约束），
   段表终稿在 SYSCALL_DESIGN.md §3.2 给出，两文以那份为准，
   本文不另拟。IDT 的选择子常量（§2.2）在新 GDT 落地时
   按终稿复核——若内核代码段仍为 0x08 则 IDT 零改动，这也是
   终稿把内核代码段放在 0x08 的理由之一。

## 9. 启动顺序与验收清单

kmain 中的中断相关顺序（契约，调整须同步改 interrupts.h 的
注释）：

```
pmm_init → VMM 自检 → sched_init（idle 就位）
  → interrupts_init()   装 IDT、PIC 重映射全掩码；IF 仍为 0
  → 创建内核线程        trampoline 里 sti 已安全（无源可响）
  → timer_start()       PIT 编程、放行 IRQ0、sti —— 抢占自此生效
  → M2 自检             忙等双线程被 tick 轮转 + 睡眠任务按时醒
  → （开关开启时）探针 A，故意 #PF，转储后停机为预期终局
```

验收清单（每项都是串口可判的事实）：

- 双忙等线程（不调用 yield）在数秒内计数交替增长，量级相当
  ——证明抢占而非协作；
- `sched_sleep_ticks(50)` 的任务在约 0.5 s 后打印苏醒行，
  且不早于 49 个 tick（睡眠语义「至少」不被破坏）；
- idle 在无活时不忙转：全程只有 idle 时串口无持续输出、
  uptime 仍在推进（tick 在 hlt 间正常到达）；
- 探针 A 的 #PF 转储字段齐全且与构造值一致（§7.4）；
- 宿主机侧：`sched_tick()` 的纯逻辑部分（唤醒扫描、扣片、
  idle 让位判定）应随 sched 的 hosted 测试补用例——tick 逻辑
  在 sched.c 内、与硬件无关，没有理由只靠开机验（提案补
  `tests/test_sched.c` 用例若干）。

## 10. 风险清单

1. **最大风险：三重故障哑火链仍未断**。当前无 TSS、无 IST、
   异常桩不保存寄存器：若内核栈溢出引发 #PF，推帧本身再次
   缺页升级为 #DF，#DF 再失败即三重故障，机器直接复位，
   串口一个字都不留——恰好在最需要黑匣子的故障上没有黑匣子。
   §8 的 GDT/TSS+IST 是唯一的根治，且它同时是 Ring 3 的
   前置件，建议总协调将其排期提前到 M3 之前而不是之后；
   在它落地前，内核栈深度纪律（tick/异常路径浅调用链、
   大局部数组禁止上栈）是仅有的缓解，须靠评审守住。
2. **IDT 选择子与 stub GDT 的隐性耦合**（§2.2/§8）：UEFI
   正式引导链替换 stub 时若 GDT 布局变化而 IDT 常量未同步，
   症状是第一次中断即三重故障，极易误判到 PIC/PIT 头上。
   缓解已定：常量单点定义 + 在引导链切换的验收单里把
   「触发一次探针 A」列为必过项。
3. **EOI 顺序被后人「优化」掉**：先 EOI 后 sched_tick 看似
   反直觉，将来有人把 EOI 挪到 handler 末尾「更整齐」，时钟
   会在首次抢占后静默死亡且协作路径一切正常，极难定位。
   缓解：interrupts.c 该行注释须写明 §4.4 的理由（本文已
   备好措辞），并把「抢占后 tick 仍持续」列入每次改动的
   回归眼查项。
4. **PIT 的长期地位**：PIT 在部分新硬件/虚拟化环境里是模拟
   的，频率精度与延迟抖动不如 LAPIC timer；本阶段 QEMU
   目标下无碍，但真机里程碑时须重估——届时换源不动
   `sched_tick()` 接口（§1.2 已隔离），成本可控，记账在此。
5. **中断延迟不可见**：tick 里若混入慢操作（如有人加了打印），
   表现为全系统周期性卡顿而非崩溃，无转储可查。§5.3 的铁律
   靠评审执行；另提案在 tick 内留一个廉价的自检计数（handler
   执行次数与 uptime 对账），跑偏时能在自检段被发现。
