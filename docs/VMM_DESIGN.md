# Yousj OS · 虚拟内存（VMM）设计

> 状态：设计稿，待总协调评审。阶段 1 第 2 步（PMM 之后、调度器之前）。
> 范围：x86_64 四级页表、服务器无头构建。本文所有新增函数、结构与
> 常量均为**接口提案**，标注为「提案」；未获总协调批准前，不视为
> `kernel/include/yousj/` 的既定接口，不得据此自行改头文件。
> 既有事实以已落地代码为准：`pmm.h`/`pmm.c`（`YOUSJ_PAGE_SIZE=4096`、
> 失败返回 0、首 1 MiB 保留、位图上限 8 GiB）、`boot.h`（内存图是物理
> 内存的唯一真相来源）、`kmain.c`（当前只有串口输出，PMM 初始化后停机，
> 下一步即 VMM）。

## 1. 目标与非目标

### 1.1 本阶段目标

1. 内核从引导阶段遗留的页表（具体由 Bootloader 一侧决定，本设计不假设
   其布局，只假设 kmain 运行时已开启分页且能取到当前 CR3）接管分页，
   建立一份由内核自己拥有、可复现、可自检的页表。
2. 给内核代码、数据、栈、堆（后续）和页表自身提供稳定、与物理内存大小
   无关的虚拟地址，保证后续调度器、系统调用、ELF 加载都建立在同一套
   地址常量上，不再回头改布局。
3. 给未来用户进程预留低半区地址空间与每进程独立页表的机制；本阶段
   只建内核空间与「创建/销毁一份空白用户空间」的能力，不做按需调页
   （demand paging）、写时复制（COW）和 swapping，这些留阶段 2。
4. 页表逻辑可在宿主机上单测（沿用 PMM 的做法：同一份逻辑代码，
   freestanding 与 hosted 两种编译），不必每次开机验证。

### 1.2 非目标

- 不做五级页表（LA57）：四级 256 TiB 可寻址空间对当前 8 GiB 物理
  上限绰绰有余，CPU 是否支持 LA57 还要在运行时探测，平白增加一条
  代码路径，不做。将来真要上，在 `vmm_init` 探测 CPUID 后再议。
- 不做大页的通用分配接口：直接映射区内部可用 2 MiB 大页优化（见
  §3.4），但对外接口一律以 4 KiB 页为粒度，避免阶段 1 就出现两种
  粒度的 unmap/拆分语义。
- 不做 NUMA、多处理器（SMP）TLB shootdown：当前是单核 bring-up，
  本地 `invlpg`/重载 CR3 足够。接口上预留说明，SMP 时再补 IPI 逻辑。
- 不做内核地址空间布局随机化（KASLR）、不做页表隔离（PTI）：服务器
  先行阶段没有对应的威胁模型优先级，记入 §9 风险清单，不假装已解决。

## 2. 总体选型：higher-half 内核 + 高半区直接映射，低半区恒等映射只作过渡

### 2.1 两个候选

- **纯恒等映射（identity map）**：虚拟地址 == 物理地址，全程 1:1。
  好处是简单、页表页的物理/虚拟转换是恒等函数、早期调试直观。
  坏处是致命的：内核与用户共用同一地址区间，用户程序（Linux ELF
  默认加载在 `0x400000` 起、栈在低地址高位）必然与内核映像、物理
  内存直映射撞车；将来每个进程一张页表时，内核必须在每张表里重复
  映射全部物理内存，且用户地址空间被切碎，没有干净的「低半区归
  用户、高半区归内核」的分界。阶段 2 的 ELF 加载会被迫返工。
- **Higher-half 内核**：内核映像与内核数据放在 canonical 地址的
  高半区（如 `0xFFFFFFFF80000000` 起），物理内存通过高半区的一个
  大窗口（直接映射区，direct map / HHDM）线性映射，用户进程独占
  低半区。高半区在每张进程页表里内容相同（共享），切换 CR3 时
  内核始终可见。

### 2.2 推荐：higher-half（结论）

**推荐采用 higher-half 布局，恒等映射仅保留为从 Bootloader 页表
切换到内核自有页表的那一小段过渡手段，切换完成后立即拆除低地址
恒等映射（保留与否见 §3.3 的例外）。**

理由，结合本项目的服务器无头场景：

1. **用户空间必须整块干净**。阶段 2 要跑未修改的 Linux ELF，其
   链接布局假设独占低半区。只有 higher-half 能一次划清界线，
   本阶段把常量定死，后面 ELF 加载、mmap/brk 布局不用再动。
2. **直接映射让页表操作可写成普通 C 代码**。有了 HHDM，
   「物理地址 P 的页表页」就是「虚拟地址 `PHYS_TO_VIRT(P)` 处的
   512 个 u64」，不需要递归映射那种自引用页表的绕脑技巧，也不需要
   每次改页表都临时映射。单核、无头、以串口日志为主要调试手段的
   环境里，可读性就是可靠性。
3. **服务器无头意味着不需要为帧缓冲等低地址设备做特殊照顾**。
   `boot.h` 的帧缓冲字段在服务器构建里不用；串口是端口 I/O
   （`inb/outb`），根本不经过分页。桌面版将来需要映射帧缓冲时，
   它是一个明确物理地址的 MMIO 区间，用 §5 的 `vmm_map` 在高半区
   显式映射即可，不构成保留全局恒等映射的理由。
4. **代价可控且一次性**：代价是链接脚本要把内核链到高地址、入口
   汇编要做一次「低地址启动 → 建表 → 跳高地址」的跳跃。这部分是
   Bootloader/入口侧的一次性工作（属总协调与 A 路地盘衔接），
   在阶段 1 付清，比在阶段 2 每个子系统里反复付便宜。

### 2.3 与 Bootloader 的衔接假设（须总协调确认）

- 本设计假设进入 kmain 时分页已开（长模式必然），但**不假设**
  Bootloader 页表映射了哪些区间、内核当前运行在低地址还是高地址。
- 因此 `vmm_init` 的姿势是：不修改 Bootloader 的页表，从 PMM 另申请
  页构建全新 PML4，先用 Bootloader 现有映射能访问的方式完成建表，
  再切 CR3 到新表（见 §6 的切换顺序）。这要求建表期间能按物理地址
  访问新页表页——若当时尚无 HHDM，就需要 Bootloader 至少恒等映射
  了可用的物理内存。此点是跨地盘接口问题，**须在实现前由总协调
  与 Bootloader 一侧对齐并回填本文**，不能靠猜。

## 3. 地址空间布局（提案常量）

### 3.1 全景（canonical low / high 两半）

四级页表下 canonical 低半区为 `0x0000000000000000`–`0x00007FFFFFFFFFFF`
（PML4 索引 0–255），高半区为 `0xFFFF800000000000`–`0xFFFFFFFFFFFFFFFF`
（PML4 索引 256–511）。布局提案如下（名字与数值均为**提案**）：

| 区间 | 起始（提案） | 大小 | 用途 |
|---|---|---|---|
| 用户空间 | `0x0000000000000000` | 128 TiB（PML4 0–255） | 每进程私有：ELF、堆、mmap、栈。布局细节属阶段 2，本文只划界 |
| （非 canonical 空洞） | `0x0000800000000000`–`0xFFFF7FFFFFFFFFFF` | — | 任何访问必 #PF，永不映射 |
| 直接映射区 HHDM | `0xFFFF800000000000`（`YOUSJ_HHDM_BASE`） | 当前最多 8 GiB（受 PMM 上限，见 §7）；预留 PML4 256 整段 | 全部物理内存线性映射，偏移 `YOUSJ_HHDM_OFFSET` |
| 内核映像区 | `0xFFFFFFFF80000000`（`YOUSJ_KERNEL_BASE`，-2 GiB 模型） | 2 GiB 窗口内实际用映像大小 | 内核 text/rodata/data/bss、内核栈（初期） |
| 固定映射/MMIO 区 | `0xFFFFFFFFC0000000` 起（提案） | 若干页 | 将来帧缓冲、LAPIC/IOAPIC 等设备的按需显式映射 |

选择 `-2 GiB` 放内核映像，是为了与常见小代码模型（`-mcmodel=kernel`
要求代码位于顶部 2 GiB）兼容；当前 Makefile 尚未加该选项，**提案：
实现 VMM 时同步给内核 CFLAGS 加 `-mcmodel=kernel`**（是否采用由
总协调定，但布局与代码模型必须配套，不能各行其是）。

### 3.2 内核空间与用户空间如何分

- **分界线就是 canonical 分界**：PML4 索引 < 256 为用户，>= 256 为
  内核。页表项的 U/S 位再做第二道闸：高半区所有映射 U/S=0，
  Ring 3 代码即使算出内核地址也访问不了。
- **内核半区共享**：每份新建的用户地址空间，其 PML4 的 256–511 项
  直接拷贝自内核主 PML4（kernel master）。这样切到任何进程的 CR3，
  内核代码、中断、系统调用入口都立即可用，不需要「先切回内核页表」
  的额外动作。拷贝的是顶层项；其下各级页表页由所有进程共享同一批
  物理页（只读共享，内核改高半区映射时须同步所有存活空间——见
  §5.4 的约束，本阶段内核高半区在 init 后基本静态，把该问题控制住）。
- **用户半区私有**：每份空间 PML4 的 0–255 项各自独立，页表页、数据页
  都归该空间所有，销毁时逐级回收（见 §5.3）。
- **空指针护栏沿用 PMM 约定**：虚拟地址 0 所在页永不映射（用户、内核
  皆然），与 PMM「物理页 0 永不分配」相互呼应，空指针解引用必 #PF。

### 3.3 过渡恒等映射的拆除与一个例外

切到自有 PML4 后应清掉低半区的恒等映射条目，使「误用物理地址当
指针」立刻 #PF 而不是悄悄成功——这是把 bug 暴露在 bring-up 期而不是
量产期的关键决定。唯一可保留的例外：若某段早期代码（如 APIC 探测前
的实模式遗留数据、未来的 trampoline 多核启动）需要低地址访问，
**逐项列明、单独映射、用完即拆**，不保留整片 1:1 映射兜底。

### 3.4 页粒度策略

- 通用接口粒度：4 KiB。
- HHDM 内部优化（可第二步再上）：物理内存对齐且连续 2 MiB 的区间
  用 PDE 的 PS 位建大页映射，8 GiB 只需 4096 个大页项、4 页 PD 级
  页表即可覆盖，能省下 4 KiB 粒度下约 2048 张 PT 页。但大页让 HHDM
  的「拆开某一页改属性」变复杂；本阶段 HHDM 属性统一（可读写、
  可执行关闭、仅内核），不需要逐页改，因此大页安全。**推荐顺序：
  先全 4 KiB 打通并自检，再把 HHDM 换大页作为独立小步并重跑自检。**
- 内核映像按节属性分别映射：`.text` 只读+可执行，`.rodata` 只读+
  NX，`.data/.bss` 可读写+NX，栈页另加一页不可访问的 guard page。
  这要求链接脚本给出各节的物理/虚拟边界符号（提案，随实现提）。

## 4. 页表结构与条目编码

### 4.1 四级走表

虚拟地址切分（4 KiB 页）：

```
63        48 47     39 38     30 29     21 20     12 11        0
|  符号扩展  |  PML4 索引 |  PDPT 索引 |  PD 索引  |  PT 索引  | 页内偏移 |
              9 bit     9 bit      9 bit     9 bit     12 bit
```

各级表都是恰好一页、512 个 `uint64_t` 条目。条目低 12 位为标志，
物理地址占位 12–51（掩码提案 `YOUSJ_PTE_ADDR_MASK =
0x000FFFFFFFFFF000ULL`）。

### 4.2 标志位（提案命名，数值是硬件定义）

| 名称（提案） | 位 | 含义 |
|---|---|---|
| `YOUSJ_PTE_PRESENT` | 0 | 条目有效 |
| `YOUSJ_PTE_WRITABLE` | 1 | 可写（只读须同时注意 CR0.WP，内核只读映射才生效，实现时须置 WP=1） |
| `YOUSJ_PTE_USER` | 2 | Ring 3 可访问 |
| `YOUSJ_PTE_NX` | 63 | 不可执行；生效前提是 EFER.NXE=1，`vmm_init` 须先置位并校验 |

对外接口不直接暴露硬件位，另设抽象标志（提案）`YOUSJ_VMM_READ /
WRITE / EXEC / USER`，由逻辑层翻译成硬件位——这层翻译是纯函数，
是宿主机单测的重点之一（见 §8）。

### 4.3 页表页的来源与记账

- 每一张页表页（PML4/PDPT/PD/PT）都来自 `pmm_alloc_page()`，一页
  恰好装一张表，不做 slab、不与其它数据混页。
- 页表页不走 `pmm_alloc_pages` 的连续分配：四级走表只需要单页，
  这正好避开 PMM 首适合（first-fit）连续分配在碎片化后的失败风险。
- 记账约定：页表页在 PMM 看来就是普通已用页；VMM 自己不另记总数，
  但 `vmm_destroy_space` 必须做到「建表时从 PMM 拿了多少页，销毁时
  一页不少地还回去」，以 PMM 的 free 计数在自检里对账（见 §8.3）。

## 5. 接口提案（待总协调批准）

> 本节全部为**提案**。返回值统一用「0 成功、负数失败」的内核风格，
> 错误码数值对齐 Linux errno 以便将来 syscall 层直接透传（提案）：
> `-EINVAL=-22`、`-ENOMEM=-12`、`-EEXIST=-17`、`-ENOENT=-2`、
> `-EFAULT=-14`。

### 5.1 地址空间对象（提案）

```c
/* 提案，待批准 */
struct vmm_space {
    uint64_t pml4_phys;   /* CR3 的值（页对齐物理地址） */
    /* 本阶段单核无锁；将来 SMP 在此加锁与引用计数 */
};
```

提案函数集：

```c
/* 提案，待批准 */
int  vmm_init(const struct yousj_boot_info *boot_info); /* 建内核主空间+HHDM，切 CR3 */
struct vmm_space *vmm_kernel_space(void);
int  vmm_create_space(struct vmm_space **out);          /* 新空间：高半区共享、低半区空白 */
void vmm_destroy_space(struct vmm_space *space);        /* 只回收用户半区与各级页表页 */
int  vmm_map(struct vmm_space *space, uint64_t virt, uint64_t phys,
             uint64_t length, uint32_t flags);
int  vmm_unmap(struct vmm_space *space, uint64_t virt, uint64_t length);
int  vmm_translate(struct vmm_space *space, uint64_t virt,
                   uint64_t *phys_out, uint32_t *flags_out);
int  vmm_protect(struct vmm_space *space, uint64_t virt, uint64_t length,
                 uint32_t flags);
```

### 5.2 `vmm_map` 语义与失败语义

- 参数校验：`virt`、`phys`、`length` 必须页对齐且 `length > 0`；
  区间不得跨越 canonical 空洞，不得跨越用户/内核分界；映射到内核
  半区时 `space` 必须是内核空间或明确走「改主空间并同步」路径
  （§5.4）。任一不满足返回 `-EINVAL`，**不做任何修改**。
- 已占用即失败：目标区间内任一页已有 present 映射，返回 `-EEXIST`，
  不覆盖、不部分修改。调用方要换映射须先显式 `vmm_unmap`。此约定
  宁可啰嗦，也杜绝「map 悄悄盖掉旧映射、旧物理页从此泄漏」。
- **全有或全无（原子性）**：先完整走查/预分配所需中间页表页，再逐页
  落条目；中途 PMM 分配失败（返回 0）则回滚本次调用新建的中间页表页
  与已落条目，返回 `-ENOMEM`，地址空间回到调用前状态。回滚时只许
  释放本次新建的页表页，绝不释放调用前已存在的——实现上在建表路径
  里记录本次新建页表页的物理地址小数组（最深 3 级、每级至多按区间
  页数增长，跨 PD 边界的大区间须分段处理，此细节留实现时按 §8 的
  故障注入测试逼出来）。
- 成功后由 VMM 负责对受影响地址做本地 TLB 失效（`invlpg` 逐页；
  区间大到超过一页 PT 时可改为重载 CR3，实现里定阈值并注释）。

### 5.3 `vmm_unmap` / `vmm_translate` / `vmm_protect` 语义

- `vmm_unmap`：区间必须页对齐；**允许区间内有未映射的洞**（逐页跳过），
  返回 0——因为进程退出、munmap 清理等调用方按区间清理是常态，
  要求精确命中会逼得调用方先逐页 translate。解除后，若某级页表页
  整页条目全空且不是共享的内核半区页表页，则回收该页表页给 PMM，
  逐级向上直到 PML4。数据物理页**不**由 VMM 释放：VMM 只管映射关系，
  物理页所有权在调用方（进程管理/文件系统），这是与 PMM 分工的
  硬边界，防止双重释放。
- `vmm_translate`：纯走表查询，不改变任何状态。地址未映射（任一级
  not present）返回 `-ENOENT`；成功时输出页基物理地址（不含页内
  偏移，调用方自行加 `virt & 0xFFF`）与抽象标志。此函数也是自检与
  #PF 处理将来判断「映射是否存在」的主要工具。
- `vmm_protect`：只改已映射页的标志，不建新映射；区间内任一页未
  映射返回 `-ENOENT` 且不做部分修改（与 map 一致的全有或全无）。
  改完同样做 TLB 失效。
- `vmm_destroy_space`：内核空间永不销毁（传入即忽略/断言， freestanding
  下以串口打印+停机暴露 bug，本阶段风格与 kmain 现有 halt 一致）。
  用户空间销毁：遍历低半区，把用户数据页的处置权交回调用方提供的
  回调或由调用方先行清理（提案：销毁函数只回收页表页本身，用户数据
  页由进程退出路径先 unmap 并释放），最后释放 PML4 页。细节签名
  待与调度设计（SCHED_DESIGN.md 的进程退出路径）对齐后定稿。

### 5.4 内核半区修改的约束

`vmm_init` 之后，内核半区映射原则上冻结。确需新增（如 MMIO 固定映射）
时，必须走「改 kernel master → 对每份存活用户空间同步其 PML4 高半区
条目」的路径；因为高半区下级页表是共享物理页，只改 PML4 项指向即可，
下级自然一致。本阶段进程数小，全量遍历同步的成本可接受；这也是不在
本阶段引入「内核半区缺页时从 master 同步」那种隐式 fault-in 机制的
理由——显式同步更易自检。

## 6. 从 PMM 申请页表页的流程与 CR3 切换时机

### 6.1 单次建表流程（`vmm_map` 内部）

```
1. 校验参数（对齐/范围/分界）                —— 失败 -EINVAL，不动状态
2. 由 space->pml4_phys 经 HHDM（过渡期用恒等/现映射）得到 PML4 指针
3. 逐级向下：PML4[i] -> PDPT -> PD -> PT
   - 条目 present：顺指针下行
   - 条目为空：p = pmm_alloc_page()
       - p == 0：回滚本次已新建的页表页，返回 -ENOMEM
       - 将 p 整页清零（经 HHDM 写，清零是强制项：脏条目会被 CPU
         当合法映射，是最难查的一类 bug）
       - 写入上级条目：地址 | PRESENT | WRITABLE |（该级以下若含
         用户页则置 USER，权限取各级交集是硬件规则，中间级不许
         比叶子更严地误杀：本设计中间级一律给 PRESENT|WRITABLE|
         (USER 按空间半区)，真正的权限收紧只放在叶子条目）
4. 在 PT 写入叶子条目：phys | 翻译后的标志
5. 若改的是当前 CR3 正在使用的空间：invlpg / 必要时重载 CR3
```

关键纪律：**申请到的页表页先清零再挂入树中**；顺序反过来（先挂入、
后清零）在单核关中断下尚可，但一旦将来有中断/多核就会读到脏表，
现在就定死顺序，成本为零。

### 6.2 `vmm_init` 的整体顺序（提案）

```
pmm_init（已完成，kmain 现有）
  -> vmm_init:
     a. 校验/设置 CPU 能力：EFER.NXE=1、CR0.WP=1；读当前 CR3 仅作记录
     b. 分配 PML4 页，清零
     c. 建 HHDM：按 boot_info 内存图，把全部 usable + 需要访问的
        reserved/MMIO 物理区间映射到 HHDM 基址（属性 RW、NX、内核）
     d. 建内核映像映射：按链接脚本符号把映像各节按 §3.4 属性映射
        到 YOUSJ_KERNEL_BASE；含内核栈与 guard page
     e. （过渡）保留 Bootloader 给出的低地址可达性，直到切换完成
     f. 切 CR3 = 新 PML4；随即以高半区地址重取栈指针/跳入高半区
        继续执行（此步含一小段汇编跳板，属入口地盘，须总协调排期）
     g. 在新空间内拆除过渡恒等映射，invlpg/重载 CR3 使之生效
     h. 串口打印自检结果（见 §8.3），失败即 halt，不带病前进
sched_init（下一步，SCHED_DESIGN.md）
```

### 6.3 CR3 切换时机汇总

| 时机 | 动作 |
|---|---|
| `vmm_init` 完成建表 | 一次性从 Bootloader CR3 切到内核主空间 CR3（§6.2 f） |
| 进程调度切换（调度器落地后） | 仅当下一个任务的地址空间 != 当前空间时写 CR3；同空间线程切换不写，避免无谓 TLB 全刷。写 CR3 放在上下文切换汇编里、恢复新任务寄存器之前（详见 SCHED_DESIGN.md） |
| 内核线程运行 | 内核线程无自有空间，借用「上一个用户空间或内核主空间」——统一约定借内核主空间，使 CR3 取值可预测（详见 SCHED_DESIGN.md） |
| 地址空间销毁后 | 严禁任何存活任务的 CR3 仍指向已释放的 PML4：销毁只能发生在该空间已无任务运行、且当前 CR3 不是它之后；由进程退出路径保证（先切走、后销毁） |
| 本阶段不做 | PCID/ASID（CR3 低 12 位恒为 0）、五级页表切换、中断路径中切 CR3 |

写 CR3 本身即完成该 CPU 的 TLB 刷新（非 global 页），本阶段不设
global 页（PGE 不启用），省去区分 flush 范围的麻烦；性能优化留后。

## 7. PMM 的 8 GiB / 位图上限对 VMM 的影响与风险

PMM 现状（`pmm.h`）：两位图各 `256 KiB` 在 BSS，最多描述
`YOUSJ_PMM_MAX_PAGES = 2,097,152` 页 = 8 GiB；内存图超出部分
`pmm_truncated()` 为真并被直接忽略。影响如下：

1. **物理寻址天花板就是 8 GiB**。VMM 的 HHDM 只需、也只能映射
   8 GiB；超过 8 GiB 的物理内存本阶段不存在于任何数据结构中，
   不是「映射不到」，是「系统不知道它存在」。服务器版若部署到
   大内存机器，内存被静默截断——因此 `vmm_init`/kmain 必须在
   `pmm_truncated()` 为真时在串口明确告警（现状 kmain 已打印
   truncated 提示，须保留并升级为显式告警行），不能装作有全部内存。
2. **页表页预算要按 8 GiB 最坏情况算**。全 4 KiB 粒度时，仅 HHDM
   就需要 1（PML4 共用）+ 8（PDPT 项内）…按区间算：8 GiB / 4 KiB =
   2M 页 → PT 页 4096 张 + PD 页 8 张 + PDPT 1 张 ≈ 16 MiB 物理内存
   纯做页表，占总内存比例小，但这 16 MiB 必须在建 HHDM 时由 PMM
   一次次供出；若机器实际只有 64 MiB 级别内存，占比升到 25%，
   不可忽视——这也是 §3.4 推荐 HHDM 尽早换 2 MiB 大页（降到约
   5 张页表页）的硬理由。
3. **用户空间的页表开销无上限保护**。一个进程把低半区大面积映射时，
   中间页表页消耗可达映射量的约 0.2%（4 KiB 粒度），本身不大；
   但恶意/失控进程可只建映射不落数据页来吃页表页。本阶段无进程
   资源限额，先在设计上留账：页表页消耗应能按空间统计（提案：
   `vmm_space` 后续加页表页计数字段），阶段 2 做 rlimit 时有据可依。
4. **位图在 BSS 而不在被管内存里**，意味着扩大上限只需改常量并付
   BSS 体积（每扩 8 GiB 付 512 KiB BSS），这是将来最便宜的扩容
   路径；但在那之前，VMM 的任何常量（HHDM 预留、 translate 的合法
   物理上限校验）都应从 `YOUSJ_PMM_MAX_PAGES` 推导或与之断言一致，
   不许在 VMM 里再写死一个不同的「最大内存」数字，两处不一致必然
   在扩容那天爆掉。
5. **首 1 MiB 保留与 HHDM 不冲突**：HHDM 是虚拟窗口，映射物理 0 页
   本身无妨（只是访问低物理内存的窗口），但为防误触，HHDM 内对应
   首 1 MiB 的条目建议不映射（保持与 PMM「不可用」语义一致）；
   真需要访问 BIOS 数据区时单独临时映射。

## 8. 自检方案：纯逻辑与硬件动作的拆分

沿用 PMM 的成功经验：`pmm.c` 能同时以 freestanding 与 hosted 编译，
逻辑错误在宿主机上被单测抓住（双位图那个 bug 就是这么抓的）。
VMM 必须同样拆分，否则每改一行都要开机看串口。

### 8.1 拆分边界（提案的文件/函数划分）

| 层 | 内容 | 可宿主机测试 |
|---|---|---|
| 纯逻辑层 | 地址切分（各级索引、页内偏移）、抽象标志↔硬件位翻译、条目编码/解码、参数校验（对齐/范围/跨界）、走表算法本身 | 是 |
| 物理内存抽象层 | 「按物理地址读/写一页页表」与「向 PMM 申请/释放一页」做成一对可替换的后端操作：内核构建里走 HHDM+PMM；宿主机测试里走一块大数组模拟的「物理内存」+ 计数型假分配器 | 接口同构，两边共用逻辑层 |
| 硬件层（薄） | 读/写 CR3、`invlpg`、EFER/CR0 设置、高半区跳转跳板 | 否，只做开机自检 |

走表算法只通过抽象层碰「物理内存」，不直接解引用任何指针——这是
能单测的前提，也是本设计对实现的最硬一条结构要求。

### 8.2 宿主机单测清单（提案，`tests/test_vmm.c` 方向）

1. 索引切分：对一组边界地址（0、页尾、跨 PT/PD/PDPT 边界、
   canonical 分界两侧、HHDM 基址、内核基址）断言四级索引与偏移。
2. 标志翻译：每种抽象标志组合 ↔ 硬件位的往返一致；NX 位位置正确。
3. 建表与查询：模拟内存上 map 一页 → translate 回同一物理地址与
   标志；map 一段跨 PD 边界的区间 → 逐页 translate 全对。
4. 失败语义：未对齐参数 `-EINVAL`；重复 map `-EEXIST` 且原映射
   不变；translate 未映射地址 `-ENOENT`；protect 未映射区间
   `-ENOENT` 且无部分修改。
5. **故障注入**：假分配器在第 N 次分配时返回 0（模拟 OOM），
   断言 map 返回 `-ENOMEM`、已建部分全回滚、假分配器的
   「已分配页数」回到调用前数值（页表页一页不泄漏）。
6. unmap 回收：map 一整段后 unmap，断言数据页未被误释放（假分配器
   计数只减少页表页那部分）、空页表页被逐级回收、PML4 本身保留。
7. 空间隔离：两个空间 map 同一虚拟地址到不同物理页，互不影响；
   两者的 PML4 高半区条目与内核主空间一致。
8. destroy 对账：create → map 若干 → destroy 后，假分配器计数回到
   create 前（PML4 + 全部页表页无泄漏）。

### 8.3 开机自检（串口断言，沿用 kmain 现有风格）

在 QEMU/真机 bring-up 时，`vmm_init` 后跑一遍硬件侧自检并串口打印
PASS/FAIL，失败 halt：

- 用 PMM 申请一页数据页，分别经 HHDM 地址与一处临时显式映射写入
  魔数、互相读回比对（证明 HHDM 偏移与走表一致）；
- 对一个未映射地址做 translate 应得 `-ENOENT`（只查表不真访问，
  避免故意 #PF）；
- 读回 CR3 与 `vmm_kernel_space()->pml4_phys` 比对一致；
- 打印 PMM free 页数在自检前后的差值，与预期（临时页已释放）对账。

## 9. 风险清单

1. **最大风险：Bootloader 交接面的页表现状未知**。§2.3 的衔接假设
   若与 A 路实现不一致（例如 kmain 运行时可用映射范围比假设小），
   `vmm_init` 第一步就会 #PF 且无串口线索可看（串口是端口 I/O 不受
   影响，但 fault 时我们尚无 IDT/#PF 处理，连错误地址都打不出来）。
   缓解：实现 VMM 之前，先做一个「打印当前 CR3 并走查现有 PML4」
   的只读探针步；并且 IDT+最简 #PF 串口转储应排在 VMM 之前或与之
   同批落地（此排期建议请总协调裁决，涉及调度设计的前置依赖）。
2. 页表页清零顺序、权限中间级设置这类「错了不立刻炸、量产才炸」
   的细节，只能靠 §8.2 的故障注入与逐项断言防住，不能靠肉眼 review。
3. 内核半区共享 + 显式同步（§5.4）在进程数变大后是 O(进程数) 的
   同步成本；若将来频繁动态映射内核区，需要改走 master fault-in
   机制，届时本文 §5.4 须修订，勿把现约定当永久设计。
4. 8 GiB 截断在服务器部署时是真实容量风险（§7.1），告警不可省；
   扩容路径已留（改 PMM 常量付 BSS），但 HHDM 大页优化未落地前，
   扩容会同步放大页表页开销，两个改动要一起评估。
5. 未做 PTI/KASLR：对当前自用 bring-up 可接受，但「服务器版对外
   提供服务」之前必须重估，尤其是 syscall 入口与 Meltdown 类问题，
   记录在此防止被遗忘。

## 10. 落地顺序（给实现者的小步清单）

1. 纯逻辑层 + 宿主机单测（§8.2 第 1–4 项）先行，`make test` 绿。
2. 接入模拟分配器的故障注入与回收对账（§8.2 第 5–8 项）。
3. 内核侧 `vmm_init`：HHDM（先 4 KiB）+ 内核映像映射 + CR3 切换 +
   开机自检（§8.3），串口 PASS 后再拆过渡恒等映射。
4. `vmm_create_space/destroy_space` + 一个「空白用户空间」冒烟：
   建空间、map 一页、切 CR3、translate 验证、切回、销毁、对账。
5. HHDM 换 2 MiB 大页，重跑全部自检。
6. 至此交调度器：CR3 切换点与空间生命周期按本文 §6.3 与
   SCHED_DESIGN.md 对接。
